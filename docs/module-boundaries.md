## 向清洗同学交接：两个众数缺陷及报告口径

### C-01：初始坐标后续出现时的计数没有同步

证据：`cleaning.clean._majority_coordinates()` 使用 `counts.setdefault(base, locations[location][2])`。冲突字典第一次建立后，后续相同初始坐标只更新 `locations` 里的数量，已存在的 `counts[base]` 不刷新。

复现：同一地点的五条不同用户记录，坐标顺序为 A、B、B、A、A。真实 A=3、B=2，但冲突字典保留 A 的旧计数 1，当前选 B。`sample/review-anomalies.tsv` 的 `synthetic-plaza` 就是该情形：A=(30.27,-97.75)，B=(31.27,-96.75)。

影响：输出地点坐标错误，随后速度判断、矩形 / 半径查询和地图位置都会受影响。建议模块负责人使用实时完整计数选众数，保留可解释的平票策略并增加该回归；本轮全栈未实施此算法修改。

### C-02：初始坐标本身为众数时不生成修复目标

证据：`_majority_coordinates()` 只有 `best != base` 时才写入 `fixes`。如 A、A、B，目标仍应为 A，但没有修复目标，少数 B 会保留。

建议模块负责人对所有坐标冲突地点产生统一目标，并增加首条坐标已为多数的回归。全栈不自行替换这个行为。

### C-03：`coord_repair` 不是实际变化数量

证据：Pass 2 只要存在 `fixes[location]`，就给所有该地点记录增加 `coord_repair`，包括原本已等于目标坐标的记录。

当前原样样例的清洗计数：扫描 19、剔除 7、有效候选 12、去重 2、输出 10，分片 6 / 4。上游报告 `coord_repair=5`；逐 user / location 对比实际只有 3 条坐标变化，且由 C-01 导致目标选错。两条计数对账仍成立，但对账成立不意味着质量正确。

交接建议：由清洗负责人明确指标是“处理的地点记录”还是“发生变化的记录”，必要时分别输出，不把一种口径覆盖成另一种。全栈保留原始统计，展示样本时区分观察到的变化；有限样本也不能推断全量准确率。
