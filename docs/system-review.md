# 系统全面诊断与迭代方案

审查日期：2026-11-22。对象为当前本地 `feature/checkin-query` 工作区。用户随后明确仅允许修改全栈，不允许改动其他同学的 `cleaning/`、`db/`；因此此前坐标算法修复已经撤回，这两个目录及数据库组 `compose.yaml` 按已获取的 `origin/main` 提交 `753ec0f` 原文恢复。恢复后已实际复跑：45 个自动化用例中 42 个正常通过、3 个上游清洗问题为预期失败；数据库外部兼容运行器 11 个通过。撤回前的 18 + 14 项浏览器及旧性能结果仅属历史，当前边界修订浏览器另行复跑 14/14 通过，12 个团队文件逐字节一致。详见 [验收记录](review-validation.md) 和 [模块边界](module-boundaries.md)。

## 1. 整体判断与证据范围

系统已经具有真实的数据处理主干：上传原始文件，建立持久化任务，执行完整清洗，写入两个 SQLite 用户分片，核验后切换活动批次，并提供时间、用户、地点和空间查询。它不是单纯的数据查看器。试导入不修改活动数据，正式导入不会覆盖已有快照，失败重试和批次回退也已有服务端实现。

审查起点的主要短板是：签到记录缺少导出服务，输入格式局限于 Gowalla 五列 TSV，数据质量只能看到计数、难以查看实际变化，工作台缺少解释数据规模与质量的完整摘要。这些全栈增强已实施，恢复模块边界后的代表性自动化与浏览器复验已完成。上游清洗的地点坐标众数仍有确定缺陷，必须交清洗同学处理；全栈保持原样调用和真实报告，不在适配器中悄悄重做修复。

阅读与核对范围包括设计书 v3.1 已有接入说明、README、`docs/full-system.md`、历史验收及升级记录、前端页面与脚本、后端鉴权和 API、控制库、工作队列、清洗适配器、上游清洗、SQLite 入库器、批次节点及现有测试。源代码事实主要来自：

- `backend/server.py`：鉴权入口、文件上传、查询聚合、目录、批次管理和公开 API。
- `backend/control.py`、`backend/security.py`：控制库、批次可见性、账号、会话与限速。
- `backend/worker.py`：任务队列、清洗入库编排、探针、发布、回退及恢复。
- `backend/cleaning_adapter.py`、`cleaning/clean.py`：原始数据检查、清洗规则、计数及样本能力。
- `backend/spatial.py`、`backend/batch_node.py`：全栈自身的 WGS 84 查询、只读批次节点与导出；`db/load.py`、`db/schema.sql` 属数据库同学模块，仅原样调用。
- `frontend/index.html`、`frontend/app.js`、`frontend/system.js`、`frontend/style.css`：页面与状态、地图、上传、报告、导出入口和响应式布局。
- `tests/test_full_system.py`、`scripts/test_database_compat.py`：全栈回归及数据库原测试的外部兼容运行器；不为适配全栈而修改 `db/test_database.py`。阅读测试不能替代本轮实际运行。

## 5. 四种专业视角的取舍

**架构师与 GIS 开发者。** 保留 Python / Flask、原生前端、SQLite 和现有模块。格式转换负责输入差异，清洗负责数据规则，入库负责约束与索引，工作进程负责编排和发布，API 负责鉴权与查询聚合。WGS 84 经纬度用于查询与导出；Web Mercator 仅用于底图呈现。OSM 不需要 GCJ-02 偏移；如未来更换使用偏移坐标的底图，应增加明确的转换层，不能修改持久化原始坐标。

**产品经理与 UI/UX 设计师。** 首页说明“当前是什么数据、质量如何、下一步做什么”；导入页说明“选文件、映射、试导入、看报告、正式替换”；地图页说明“条件、当前批次、当前页、选择详情、导出范围”；批次页负责版本与恢复。不要把同一项功能分散成多个相似按钮，也不要增加无后端行为的占位入口。

**真实使用者。** 管理员需要确认影响范围、看见真实失败原因并能够恢复；普通用户需要直接查询、地图定位和导出，不能访问上传或激活接口；初次使用者需要可公开样例、格式说明和空状态入口。开放注册、手工编辑单条签到不是当前必要功能，任意修改批次快照还会破坏可复现性。

**课程评委。** 先看异常原始数据，再看清洗证据、真实数据库计数、用户 / 时间 / 空间组织、地图和导出，最后看失败不破坏活动数据与批次回退。技术亮点应是时空规则、分片路由、不可变快照和原子发布等实际能力，不能把“两台本机进程”称为已经部署完成的跨主机容灾集群。

## 6. 开发与验收顺序

1. 保持 `cleaning/`、`db/` 与已获取上游原文一致；将坐标准确性缺陷及样例交模块负责人，原样调用，不静默替代算法；已有数据不自动重建。
2. 实施有界导出，验证参数、鉴权、批次固定、CSV 公式风险与 GeoJSON 经度在前的坐标顺序。
3. 增加 CSV / JSON / JSONL 适配和字段映射，保留原文件来源信息；不同格式使用同一批构造记录对照。
4. 完善质量样本、工作台、地图点聚合、加载 / 空 / 错误 / 成功反馈。
5. 运行独立临时库测试和专用浏览器验收；不覆盖当前真实活动数据。逐项记录“通过 / 失败 / 未执行”。
6. 依据 [答辩演示流程](defense-demo.md) 复核管理员、普通用户和首次使用路径。

构造样例与精确预期位于 `sample/review-checkins.csv`、`.json`、`.jsonl`、`sample/review-anomalies.tsv` 和 `sample/review-oracle.json`。已通过 `git show origin/main:cleaning/clean.py` 在临时目录加载上游原文，直接运行清洗：19 个物理行，7 条剔除，12 条有效候选，重复 2，最终输出 10；调用现有 `db.load.shard_for` 得到节点 6 / 4。格式化样例有 18 条记录，没有额外空行，扫描 18、剔除 6，其余相同。

当前上游对 plaza 的 A、B、B、A、A 错选 B，报告 `coord_repair=5`，逐条比较输入输出仅 3 条坐标真正变化，而且方向错误。Austin 矩形当前命中 5 条，1500 米半径只有 u2 一条。此前本地修复版的“真实修复 2、矩形 10、半径 6”已作历史标记，不再是当前预期。这次直接运行不等于恢复后 HTTP / 浏览器端到端已通过，也不证明上游质量正确。
